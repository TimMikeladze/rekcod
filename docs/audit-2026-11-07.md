# Rekcod audit

Audit of commit `3fa2ce259755bbb23959b74686a189de4e3b70a8`, completed 2026-11-07.
There are 39 actionable findings: 23 from the first pass and 16 from
[round 2](#round-2). The first fixes should address dashboard cookie isolation,
sandbox authorization, repository symlinks on nodes, tenant storage separation,
and snapshot publication. Passing tests currently miss those paths.

No user VM or container was started, stopped, or modified. Reproductions used
synthetic credentials, temporary directories, mock processes, or in-memory
streams. Security findings have not been posted externally. What was fixed
afterwards is in [Fix status](#fix-status).

## Fix these first

| Finding | What fails | First change |
| --- | --- | --- |
| S1 | A local web service receives the dashboard's login cookie. | Keep the API credential within its browser origin and send it explicitly in a header. |
| S2 and S3 | A restricted sandbox server can change another project and reach internal fleet operations. | Authorize every target sandbox and separate node-only operations. |
| S4 and S5 | Filesystem aliases and repository symlinks bypass intended boundaries. | Protect Git metadata using filesystem identity; read and write repo files without following links. |
| F1 and F2 | Bucket naming and preview naming can cross tenant boundaries. | Use disjoint storage identifiers and verify preview ownership before upsert. |
| D1 through D4 | Backups can become inconsistent, restore can select the wrong data, streams can truncate silently, and disk recovery can format existing data. | Make generation selection explicit, propagate read errors, and require fresh-disk provenance. |
| S6 and S7 | Apply writes symlink chains that leave the project, and a concurrent diff changes what `--reviewed` writes. | Resolve link chains against the project; lock diff and apply per sandbox. |
| F6 and F7 | Destroy during a deploy mixes owners' instances, and failed bucket cleanup is forgotten. | Lock and fence destroy; keep the app until storage cleanup succeeds. |
| D6 through D9 | Snapshots, imports, S3 downloads and controller restore can lose data while reporting success. | Disjoint marker names, daemon identity checks, exact-length reads, strict restore validation. |

`P1` means address before relying on the affected security or data integrity claim.
`P2` means a correctness, availability, or deployment defect. A package's upstream
severity is reported separately from its demonstrated reachability in rekcod.
**Reproduced** identifies an exercised decision or behavior; the entry states when
the reproduction used a mock or extracted source. **Source confirmed** means the
trigger and faulty branch were traced, without exercising a complete deployment.

## Access and isolation

### S1 P1 Dashboard cookies are sent to other localhost services

Source: [auth.ts:45](../dashboard/src/lib/auth.ts#L45),
[auth.ts:38](../dashboard/src/lib/auth.ts#L38),
[guard.ts:10](../dashboard/src/lib/guard.ts#L10).

The dashboard sets its bearer token in an HttpOnly cookie on `localhost`, with
`Path=/`. Cookie names contain a port, but cookie delivery does not distinguish
ports. After signing in, opening a container's web page on another localhost port
sends that service the cookie. HttpOnly stops browser JavaScript reading it; the
HTTP server still receives it. That service can replay the token to the dashboard
and run offered actions as the Mac user. Server-side requests can omit the browser
Origin and Fetch Metadata headers.

**Reproduced:** Chromium visited two temporary localhost servers. The first used
the actual `authCookie` function with a synthetic token. The second received the
cookie. Replaying it through the actual mutation guard returned no refusal:
`synthetic_cookie_sent_to_other_localhost_port=true`,
`replay_passes_actual_mutation_guard=true`. No rekcod action was executed.

Fix: keep the API credential in origin-scoped browser storage or memory and send
it explicitly in an authorization header, rather than granting API access through
a cookie that the browser automatically sends to other ports. Authenticated SSE
would need a fetch-based stream or another suitable mechanism. A separate browser
profile is another isolation option. A dedicated launch hostname and restrictive
referrer policy can reduce exposure but should not be the sole boundary: cookies
still cross ports for that hostname. Add a two-origin browser regression test;
changing only SameSite, HttpOnly, or the cookie name does not resolve the disclosure.

### S2 P1 Sandbox policy does not authorize existing sandbox IDs

Source: [sandbox_api.rs:112](../crates/rekcod/src/sandbox_api.rs#L112),
[sandbox_api.rs:147](../crates/rekcod/src/sandbox_api.rs#L147),
[sandbox_api.rs:184](../crates/rekcod/src/sandbox_api.rs#L184),
[sandbox_api.rs:442](../crates/rekcod/src/sandbox_api.rs#L442).

`Policy::project` and `Policy::check` restrict creation. Listing, reading, exec,
fork, diff, apply, stop, and removal operate on any matching sandbox in the shared
rekcod home. The HTTP exec path also bypasses `op` entirely. An MCP server started
with `--root A` can discover and operate on a pre-existing sandbox for project B,
including one with a live mount or broader network and secret permissions.

**Reproduced:** an isolated home contained a stopped synthetic sandbox for B and a
reviewed text-file change. An MCP process started with `--root A` listed that
sandbox and successfully applied the change to B. No VM was required or started.

Fix: resolve and authorize the target before every operation, including streamed
HTTP exec. Filter listing as well. Check project membership and the sandbox's
mount, secret, OS, and network capabilities against the server policy, or bind
servers to a private set of sandbox IDs. Test access to an existing broader
sandbox, rather than only rejected create arguments.

### S3 P1 The generic sandbox HTTP API exposes node-only operations

Source: [sandbox_api.rs:214](../crates/rekcod/src/sandbox_api.rs#L214),
[sandbox_api.rs:376](../crates/rekcod/src/sandbox_api.rs#L376),
[fleet.rs:782](../crates/rekcod/src/fleet.rs#L782),
[fleet.rs:815](../crates/rekcod/src/fleet.rs#L815).

`sandbox serve --root DIR` exposes `/instances` and `/jobs` through the same route
table as a fleet node. Those operations call deployment and job code without
checking `Policy`. A caller refused a Git source by the normal create operation
can submit it through an internal route instead. Job creation also selects an
open egress allowlist rather than the server's configured policy.

**Reproduced:** a temporary Unix-socket server rejected a Git create with the
expected policy error. The same source sent to `/instances` invoked host-side
Git fetch. Git was a mock that recorded arguments and failed before any network
request or VM start.

Fix: separate public sandbox and controller-to-node route tables, or add an
explicit node capability checked before dispatch. Both API surfaces need tests
that internal operations are unavailable under a user policy.

### S4 P1 Case aliases let sandbox apply write protected Git metadata

Source: [sandbox.rs:24](../crates/rekcod/src/sandbox.rs#L24),
[sandbox.rs:664](../crates/rekcod/src/sandbox.rs#L664),
[sandbox.rs:872](../crates/rekcod/src/sandbox.rs#L872),
[safefs.rs:75](../crates/rekcod/src/safefs.rs#L75).

The excluded `.git` name is compared byte for byte. On case-insensitive APFS, a
workspace entry named `.GIT` passes that check but resolves to the project's real
`.git` when applied. A new file has no manifest entry and no existing destination,
so the conflict check also permits it. Git hooks or configuration can therefore
enter the host repository despite the stated exclusion.

**Reproduced:** applying a reviewed `.GIT/audit-marker` from a synthetic stopped
sandbox wrote `.git/audit-marker` in a temporary project. The actual MCP and apply
implementation returned success. The marker was plain text; no hook was installed
or executed.

Fix: reject protected path components according to the destination filesystem's
case and normalization rules, and check destination identity before writes.
Include case aliases and Unicode normalization aliases in apply tests.

### S5 P1 Node deployment follows repository symlinks on the host

Source: [fleet.rs:657](../crates/rekcod/src/fleet.rs#L657),
[fleet.rs:662](../crates/rekcod/src/fleet.rs#L662),
[xrun.rs:60](../crates/rekcod/src/xrun.rs#L60).

Before creating the sandbox, deployment reads `rekcod.toml` through the host
filesystem. Runtime detection reads other repository files the same way. Those
reads follow repository-controlled symlinks. A symlink to a device such as
`/dev/zero` makes an unbounded host read; a readable file outside the checkout can
also influence configuration. A dangling `Dockerfile` symlink makes `exists()`
return false, after which `std::fs::write` follows it and creates the target
outside the checkout. This creates a host file; this audit did not demonstrate
overwriting an existing target or host code execution.

**Source confirmed.** No memory exhaustion or host-file attack was run.

Fix: use a directory descriptor and no-follow opens for host-side config reads,
with explicit size limits and regular-file checks. Create generated Dockerfiles
with exclusive, no-follow semantics. Prefer parsing and generating build inputs
inside the sandbox where possible.

## Fleet authorization and admission

### F1 P1 Different apps can receive the same storage bucket

Source: [fleet.rs:4271](../crates/rekcod/src/fleet.rs#L4271),
[fleet.rs:4362](../crates/rekcod/src/fleet.rs#L4362),
[fleet.rs:4372](../crates/rekcod/src/fleet.rs#L4372).

Short app keys map to `app-<key>`. Long keys map to `app-<32 hex SHA256 prefix>`.
The two naming domains overlap: a default-namespace app named that digest maps
directly to the long app's hashed bucket. Both names satisfy the app naming rules.
`bucket_env` gives each app's separate user access to that same bucket. Data can
cross namespaces, and bucket deletion can affect the other app.

**Reproduced naming collision:** a valid 62-character namespaced key and a valid
32-character default app name produced the same bucket. This was a deterministic
calculation checked against the source; live RustFS permissions were not exercised.

Fix: derive every bucket from a stable app identifier, or use disjoint prefixes
for hashed and literal names. Check uniqueness in the controller and plan a
migration that does not delete existing shared data.

### F2 P1 Preview creation can overwrite another owner's app

Source: [fleet.rs:4203](../crates/rekcod/src/fleet.rs#L4203),
[fleet.rs:4237](../crates/rekcod/src/fleet.rs#L4237),
[fleet.rs:3699](../crates/rekcod/src/fleet.rs#L3699).

A valid signed PR event for app `foo` deploys `foo-pr-N` using a system caller
with admin privileges. The closed-event branch checks `preview_of`; creation and
updates do not. If an unrelated app already holds that name, upsert replaces its
repository and deploy settings despite its owner. Its existing `secrets` column
is preserved and subsequently loaded into the new deployment.

**Source confirmed.** This requires a valid webhook delivery; it is not a bypass
of signature verification. Fork previews still require the configured label.

Fix: under the app lock and transaction, require the destination to be absent or
already a preview of exactly this base app. Use an internal preview identifier
separate from user-selected app names. Test both opened and synchronize events
against a colliding app owned by someone else.

### F3 P2 Node certificates are reserved by authority instead of hostname

Source: [fleet.rs:2043](../crates/rekcod/src/fleet.rs#L2043),
[fleet.rs:2055](../crates/rekcod/src/fleet.rs#L2055),
[fleet.rs:2067](../crates/rekcod/src/fleet.rs#L2067).

Registration checks whether another node holds the complete `host:port`
authority, then issues a certificate for only `host`. A join-token holder can
therefore request an existing node's hostname with another port and obtain a
certificate valid for that hostname. Turning that into interception additionally
requires redirecting controller traffic; this alone does not reveal a node secret.
The database insertion also precedes certificate and transport validation, so a
rejected registration can leave a node row behind.

**Source confirmed.** No network interception was attempted.

Fix: bind node identity to its public key and have the controller pin it per
node, or enforce an explicit hostname ownership policy. Validate all registration
fields before committing the row; roll back issuance failures. Preserve supported
multiple-node-on-one-host setups explicitly instead of treating ports as TLS
identities.

### F4 P1 Resource fields permit quota bypass and integer overflow

Source: [fleet.rs:3649](../crates/rekcod/src/fleet.rs#L3649),
[fleet.rs:3656](../crates/rekcod/src/fleet.rs#L3656),
[fleet.rs:3697](../crates/rekcod/src/fleet.rs#L3697),
[fleet.rs:3802](../crates/rekcod/src/fleet.rs#L3802),
[fleet.rs:3279](../crates/rekcod/src/fleet.rs#L3279).

HTTP app specs accept signed integers, narrow them to `i32`, and multiply before
widening to `i64`. Creation and scale lack positive-range checks. `instances=0`
is charged as zero while deployment uses `instances.max(1)` and launches one.
Negative counts can reduce recorded usage; large values wrap on narrowing or
overflow during multiplication. Port values also narrow without validating the
TCP port range.

**Source confirmed.** Resource exhaustion was not induced.

Fix: deserialize into validated request types; reject unsupported zero, negative,
and out-of-range values before persistence. Use checked arithmetic in a wide
integer type. Apply the same rules to app creation, scale, jobs, and sandbox
creation, including direct HTTP callers rather than only CLI arguments.

### F5 P2 Quota admission does not reserve in-flight work

Source: [fleet.rs:3683](../crates/rekcod/src/fleet.rs#L3683),
[fleet.rs:3695](../crates/rekcod/src/fleet.rs#L3695),
[fleet.rs:1548](../crates/rekcod/src/fleet.rs#L1548),
[fleet.rs:3804](../crates/rekcod/src/fleet.rs#L3804).

The app-count check happens before the namespace quota lock. Two new apps can
both pass the last available slot. CPU and memory usage count apps only after a
live release exists, so the lock around spec upsert does not reserve resources
while a new deployment is building. The scale path checks quota and updates the
spec without acquiring that lock.

**Source confirmed.** Concurrent deployment stress was not run.

Fix: check limits and reserve desired resources in one transaction covering every
admission path. Include pending deployments in usage, then release reservations
on failure. Add concurrent create and scale tests at the last available quota slot.

## Snapshot and disk integrity

### D1 P1 An interrupted push corrupts the previous remote snapshot

Source: [snap.rs:243](../crates/rekcod/src/snap.rs#L243),
[snap.rs:263](../crates/rekcod/src/snap.rs#L263),
[snap.rs:271](../crates/rekcod/src/snap.rs#L271).

Push overwrites each archive at a fixed snapshot key before publishing the new
manifest. If volume A uploads and volume B fails, the previous manifest now
points to new A and old B. Concurrent pulls can see the same mixed generation.
Local generation markers do not protect those S3 objects.

**Source confirmed.** A live S3 interruption was not induced.

Fix: upload immutable archives beneath a generation ID, record object hashes in
that generation's manifest, and publish the current manifest only after all
archives succeed. Failed uploads must leave the previous generation restorable.
Test failures between every archive and manifest publication.

### D2 P1 Pull and same-second saves can delete the intended generation

Source: [snap.rs:186](../crates/rekcod/src/snap.rs#L186),
[snap.rs:283](../crates/rekcod/src/snap.rs#L283),
[snap.rs:383](../crates/rekcod/src/snap.rs#L383).

`finish` selects the generation with the greatest `created` timestamp and deletes
the others. Pull preserves the remote timestamp, so pulling an older cloud backup
beside a newer local snapshot deletes the just-imported generation and later
restores the local one. Saves within one second tie on timestamp and are resolved
by their random generation suffix, so a successful save can discard its new data.

**Reproduced using the current parser source:** both an older imported generation
and a same-second generation were placed in the list `finish` deletes. The live
volume remained `existing-local`; `new-generation` and its marker were stale.

Fix: explicitly commit the requested generation independently of the data's
original timestamp. Serialize mutations of the same project and snapshot name.
Test pulling an older backup and two saves with the same timestamp.

### D3 P1 Vsock read failures are reported as successful EOF

Source: [vm.rs:449](../crates/rekcod/src/vm.rs#L449).

The eager reader handles `Err(_)` exactly like `Ok(0)`: it drops the sender. A
caller sees clean EOF after the bytes already received, losing the transport
error. Docker streams such as exports, logs, or attach output can therefore end
without reporting the underlying failure.

**Reproduced with the extracted current Conn implementation:** a reader producing
`payload` followed by `ConnectionReset` returned
`connection_reset_read_to_end=Ok(7), delivered="payload"`.

Fix: add an error chunk carrying the original I/O error and deliver it after
buffered bytes. Reserve EOF for a clean zero-byte read. Test reset, device error,
and spill I/O failure separately.

### D4 P1 A zeroed disk prefix is mistaken for an entirely blank disk

Source: [boot.sh:57](../guest/rootfs/etc/rekcod/boot.sh#L57),
[boot.sh:59](../guest/rootfs/etc/rekcod/boot.sh#L59),
[cli.rs:166](../crates/rekcod/src/cli.rs#L166).

If ext4 probing fails and the first 4 MiB contain zeros, boot runs `mkfs.ext4`
before trying backup superblocks. An existing disk with damage confined to that
prefix can still contain recoverable filesystem data farther into the image.
The blank-prefix fallback defeats the stronger fresh-disk marker already written
by the host.

**Reproduced predicate:** a scratch image with a zero prefix and nonzero data
afterward returned `boot_blank_predicate=true` and
`nonzero_data_beyond_prefix=true`. No formatting command was run.

Fix: initialize automatically only with trustworthy fresh-disk provenance. For
existing disks, attempt recovery or require an explicit initialization command.
Add a boot test with a zeroed primary region and intact backup-superblock data.

### D5 P2 Partial pause failure leaves containers paused

Source: [snap.rs:449](../crates/rekcod/src/snap.rs#L449),
[snap.rs:453](../crates/rekcod/src/snap.rs#L453).

The multi-container `docker pause` call uses `?` before entering the unpause
cleanup. Docker can pause one container and fail on another, for example when
one exits during the operation. The function then returns with the first
container still paused. Signal handling does not cover this ordinary error path.

**Source confirmed.** No live pause failure was induced.

Fix: install an unpause guard before starting, track each successful pause, and
restore those states on every exit path. Test partial success, rather than only
failure before any container pauses.

## Connection handling

### R1 P2 Spill accounting eventually cuts a caught-up stream

Source: [vm.rs:443](../crates/rekcod/src/vm.rs#L443),
[vm.rs:453](../crates/rekcod/src/vm.rs#L453),
[vm.rs:476](../crates/rekcod/src/vm.rs#L476).

After a reader first exceeds the 64 MiB memory buffer, all subsequent data goes
to the spill file. `spilled` counts total bytes written and never subtracts bytes
consumed. The file also retains consumed space. A long-running stream is cut at
16 GiB of cumulative spill even if its reader caught up long before then.

**Reproduced with the current Conn source and thresholds scaled to 1 KiB and
4 KiB:** the initial stall drained, two later caught-up reads succeeded, and the
third returned `ConnectionReset`.

Fix: limit outstanding unread bytes, reclaim consumed spill space, and return to
the memory path when the spill drains. Keep the eager read required by VZ.

### R2 P2 Malformed Docker requests can leave proxy connections hung

Source: [proxy.rs:31](../crates/rekcod/src/proxy.rs#L31),
[proxy.rs:44](../crates/rekcod/src/proxy.rs#L44).

The request task can return a parsing error while the response task waits for
the guest. `tokio::join!` waits for both, and the split guest writer is still
held, so the guest receives neither a request nor EOF. The connection remains
allocated instead of returning the parser error.

**Reproduced against the actual proxy module with in-memory streams:** a malformed
chunked create request did not return after the parser had sufficient input to
reject it. The test timed out after 150 ms and cancelled its own task.

Fix: cancel and close the other direction on errors, while preserving deliberate
half-close behavior for valid attach and exec streams. Test parser errors and
half-close separately.

### R3 P2 Detached UDP flows survive removal of a published port

Source: [daemon.rs:1024](../crates/rekcod/src/daemon.rs#L1024),
[daemon.rs:1127](../crates/rekcod/src/daemon.rs#L1127),
[daemon.rs:1164](../crates/rekcod/src/daemon.rs#L1164).

Port removal aborts `udp_loop`, but its independently spawned flow tasks retain
an `Arc<UdpSocket>`. An existing flow can keep the old listener bound until its
60-second idle timeout, or longer while responses continue. A recreated mapping
can fail to bind or retain traffic from the old flow.

**Source confirmed.** No user's UDP mapping was changed.

Fix: own flow tasks in the forwarding entry and cancel them together, or give
the listener and every flow a shared cancellation token. Test immediate rebind
after removing a mapping with an established flow.

### R4 P2 Dashboard log streaming ignores backpressure

Source: [stream.ts:26](../dashboard/src/lib/server/stream.ts#L26),
[stream.ts:31](../dashboard/src/lib/server/stream.ts#L31),
[events/route.ts:13](../dashboard/src/app/api/events/route.ts#L13).

Child stdout and stderr stay in flowing mode and enqueue bytes regardless of
the HTTP consumer's capacity. The 16-child limit caps processes, not queued
bytes. A slow browser viewing a noisy container can grow the dashboard's memory
without bound. The browser's 400 KB text limit does not bound the server queue.
SSE subscribers use a similar enqueue pattern.

**Reproduced:** the actual `textStream` accepted 16 MiB from a mock child without
a response-body reader and retained its data listener. The test cancelled the
stream afterward; no large memory exhaustion test was run.

Fix: adapt Node streams with backpressure, pause producers when the response
cannot drain, and apply a bounded queue policy. SSE should coalesce state updates
or disconnect lagging clients. Test a deliberately stalled response reader.

## Operations

### O1 P2 Upgrade can delete the dashboard backup after a failed copy

Source: [lifecycle.rs:100](../crates/rekcod/src/lifecycle.rs#L100),
[lifecycle.rs:104](../crates/rekcod/src/lifecycle.rs#L104),
[install.sh:56](../scripts/install.sh#L56).

Upgrade renames the old dashboard, runs `cp -R`, ignores the command's exit
status, and deletes the old copy. Disk-full or permission failures can leave a
partial dashboard while upgrade reports success. The shell installer also
deletes the existing dashboard before copying the replacement, although its
`set -e` does at least report a copy failure.

**Source confirmed.** The installed application was not upgraded or removed.

Fix: copy into a staging directory, require successful completion and required
entry files, and swap directories only after validation. Retain or restore the
old directory on failure. Test a failing copy with a synthetic installation.

### O2 P2 Concurrent failed wakes bypass the edge backoff

Source: [edge/mod.rs:193](../crates/rekcod/src/edge/mod.rs#L193),
[edge/mod.rs:198](../crates/rekcod/src/edge/mod.rs#L198),
[edge/mod.rs:224](../crates/rekcod/src/edge/mod.rs#L224).

Each request checks the failure backoff before waiting on the per-app wake lock.
If many requests arrive before the first wake fails, they all pass that check.
After failure, each queued request acquires the lock and tries another wake
because the backoff is not checked again. An unavailable sleeping app can cause
a sequence of expensive retries despite the documented cooldown.

**Source confirmed.** The ordinary successful wake path does reuse endpoints.

Fix: check both current endpoints and failure backoff after acquiring the lock,
or share one wake result among all callers. Test a burst during a failed wake,
counting calls to the controller.

### O3 P2 Docker disk permissions depend on the launching umask

Source: [paths.rs:69](../crates/rekcod/src/paths.rs#L69),
[paths.rs:74](../crates/rekcod/src/paths.rs#L74),
[cli.rs:170](../crates/rekcod/src/cli.rs#L170).

Only `run/` is explicitly restricted to 0700. The state home and `vm/` inherit
directory defaults, while `data.img` is created without an explicit private
mode. Under umask 022 and a traversable parent home, other local accounts can
read the Docker disk, including volume data and container configuration. This
does not require compromising the account that runs rekcod.

**Source confirmed and conditional on host permissions.** The user's actual
Docker disk was not opened or permission-modified.

Fix: create state directories as 0700 and VM disks as 0600, and enforce those
modes when reopening an existing installation. Extend doctor beyond the socket
directory. Test creation under a permissive umask.

## Round 2

A second pass covered job recovery, storage and backups, and the sandbox copy
workflow. It found 16 more defects. None of them invalidates a round 1 finding.
Reproductions ran the current `target/debug/rekcod` against isolated homes, mock
workers, mock Docker CLIs and localhost mock S3 servers; no VM booted.

### S6 P1 Apply follows workspace symlink chains out of the project

Source: [sandbox.rs:664](../crates/rekcod/src/sandbox.rs#L664),
[safefs.rs:75](../crates/rekcod/src/safefs.rs#L75).

Each workspace symlink is checked on its own. `b -> .` and `leak -> b/../outside`
both look relative and inside the project, but together `leak` resolves to the
project's parent. Apply writes both links. Anything on the Mac that later reads
`leak` inside the project reads the outside file.

**Reproduced:** a synthetic stopped sandbox with those two links. `apply
--reviewed` returned success; `project/leak` resolved to `../outside-marker` and
read its contents.

Fix: resolve every link target against the final project tree, link by link,
and refuse any target that leaves the project. Test chains, not single links.

### S7 P1 A concurrent diff rewrites the copy that apply --reviewed is writing

Source: [sandbox.rs:872](../crates/rekcod/src/sandbox.rs#L872).

`diff` rebuilds the reviewed copy in place and `apply --reviewed` reads it, with
no lock between them. A diff that starts while apply runs changes the bytes apply
writes. When the workspace has replaced a reviewed directory with a symlink to a
host path, apply follows that link in the rebuilt copy and writes the host file's
contents into the project.

**Reproduced:** apply wrote `unreviewed-B` for a file reviewed as `reviewed-A`.
In a second run, a reviewed regular file `z-dir/secret` was applied with the
contents of a synthetic host-only file reached through `z-dir -> ../outside`.

Fix: hold a per-sandbox lock across diff, apply and workspace replacement. Make
the reviewed copy immutable once written, and read it with no-follow opens.

### C1 P2 Apply silently reverts host permission changes

Source: [sandbox.rs:664](../crates/rekcod/src/sandbox.rs#L664).

The copy manifest records type, size and mtime, not mode. A host `chmod 600`
after the sandbox copied the project is not a conflict, and apply writes the
workspace's `0644` back over it.

**Reproduced:** `host_permission_after_apply=0o644` after a host change to `0600`.

Fix: record mode in the manifest, treat a host mode change as a conflict, and
apply mode changes the workspace made.

### C2 P2 Apply refuses a directory replaced by a file

Source: [sandbox.rs:664](../crates/rekcod/src/sandbox.rs#L664).

`diff` reports `A a` and `D a/child`. Apply then reports `a` as changed on the
host since the copy, although only the workspace changed it, and leaves the
directory in place.

**Reproduced:** `apply --reviewed` exited 1 with `changed in ... since the sandbox
copied it: a`.

Fix: apply deletions under a path before creating a file at that path, and only
call it a conflict when the host side changed.

### D6 P1 A source volume named `done` makes save delete the new snapshot

Source: [snap.rs:78](../crates/rekcod/src/snap.rs#L78),
[snap.rs:174](../crates/rekcod/src/snap.rs#L174),
[snap.rs:383](../crates/rekcod/src/snap.rs#L383).

Data volumes are named `rekcod-snap.<project>.<name>.<generation>.<volume>` and
the completion marker `....<generation>.done`. A Compose volume named `done`
collides with the marker. `docker volume create` on the existing data volume
keeps its labels, so the marker never gets `dev.rekcod.snap.done`. The parser
sees an unfinished generation and `finish` deletes it. Save still reports success.

**Reproduced with a mock Docker CLI that keeps existing-volume labels:** save
printed `saved seed for audit: 1 volume(s)` and its last command was `volume rm -f
rekcod-snap.audit.seed.<generation>.done`.

Fix: put markers and data volumes in disjoint name domains and confirm the
generation is complete before cleanup and before reporting success.

### D7 P1 Import from a context alias erases the source volume

Source: [cli.rs:823](../crates/rekcod/src/cli.rs#L823),
[cli.rs:776](../crates/rekcod/src/cli.rs#L776),
[cli.rs:782](../crates/rekcod/src/cli.rs#L782).

`import` refuses only the literal context name `rekcod`. Another context that
points at the same daemon passes. `--volumes-only --force` then empties the
destination volume, which is also the source, before `docker cp` reads it. Both
sides measure the same empty volume, so verification passes.

**Reproduced with a mock Docker CLI and synthetic `_ping`:** `audit-data: ok`,
`imported 1, skipped 0`, `source_data_survives=False`.

Fix: compare daemon identities (`docker info` ID) of source and destination and
refuse before deleting anything.

### D8 P1 S3 downloads accept a short body

Source: [s3.rs:263](../crates/rekcod/src/s3.rs#L263),
[s3.rs:361](../crates/rekcod/src/s3.rs#L361).

`Read::take(n)` caps a Content-Length body but doesn't require `n` bytes. A
connection that closes early returns a truncated object as success from `get` and
`url_get`.

**Reproduced with the actual `s3.rs`:** a response advertising nine bytes and
sending three returned `Ok(3)`, `"abc"`.

Fix: an exact-length reader that returns `UnexpectedEof` while advertised bytes
remain.

### D9 P1 Controller restore accepts an empty backup

Source: [fleet.rs:4525](../crates/rekcod/src/fleet.rs#L4525),
[fleet.rs:1216](../crates/rekcod/src/fleet.rs#L1216).

Restore validates the download with `Db::open`, which creates the schema and runs
migrations on an empty file. The empty database then replaces the controller's.

**Reproduced twice:** an empty object, and a 1000-byte Content-Length with zero
bytes sent, both printed `restored fleet-test.db ...; start the controller again`.
The restored file had the fresh schema and none of the original data. The old
database was kept beside it as `fleet.db.before-restore-*`.

Fix: open the download read-only without migrating, require the fleet schema and
`PRAGMA integrity_check = ok`, and reject empty files.

### D10 P2 S3 listing decodes XML entities twice

Source: [s3.rs:129](../crates/rekcod/src/s3.rs#L129),
[s3.rs:321](../crates/rekcod/src/s3.rs#L321).

`xml_values` unescapes the whole `<Contents>` fragment and then the `<Key>` inside
it. A key containing `&amp;` lists as `&`, and forced deletion targets a different
key and leaves the original behind.

**Reproduced with the actual `s3.rs`:** listing `report&amp;old` sent `DELETE
/bucket/report%26old` and the bucket delete failed with 409.

Fix: decode each text value once, after extracting it, including numeric
character references.

### F6 P1 Destroy during a deploy mixes two owners' instances

Source: [fleet.rs:3335](../crates/rekcod/src/fleet.rs#L3335),
[fleet.rs:2946](../crates/rekcod/src/fleet.rs#L2946),
[fleet.rs:2970](../crates/rekcod/src/fleet.rs#L2970),
[fleet.rs:3254](../crates/rekcod/src/fleet.rs#L3254),
[fleet.rs:2127](../crates/rekcod/src/fleet.rs#L2127).

`destroy_app` doesn't take the app lock. A deploy in flight registers its instance
after the app is gone. If another user recreates the name, release numbering
restarts and the stale instance joins the new app.

**Reproduced against the actual controller with a paused mock worker:** Alice
deployed, destroyed, Bob recreated the name, and both deploys finished as release
1. The edge routed `race-app` to `audit-old` (Alice's) and `audit-new` (Bob's).
The worker never received a DELETE. Without the recreate, the race leaves a live
instance with no app row, which heartbeat cleanup treats as known.

Fix: take the app lock in destroy, give each app an immutable generation, and
check it after the lock and before registering instances or publishing a release.

### F7 P1 Failed bucket cleanup is forgotten when an app is destroyed

Source: [fleet.rs:3335](../crates/rekcod/src/fleet.rs#L3335),
[fleet.rs:4441](../crates/rekcod/src/fleet.rs#L4441),
[s3.rs:308](../crates/rekcod/src/s3.rs#L308).

`destroy_app` logs a bucket error and deletes the app row anyway. `drop_bucket`
ignores user and policy revocation errors. `bucket_exists` treats any non-200
HEAD, including 500, as absent. Nothing retries, and a later app with the same
bucket name inherits a bucket the old user and policy may still reach.

**Reproduced with a localhost mock S3:** bucket DELETE returned 503 and destroy
returned 200 with no app row left. With `remove-user` and `remove-canned-policy`
returning 503, destroy also returned 200.

Fix: revoke access first, keep the app in a `destroying` state until storage
cleanup succeeds, retry from the reconcile loop, and treat only 404 as absent.

### J1 P2 Cancelling a job while it prepares doesn't stop it

Source: [fleet.rs:882](../crates/rekcod/src/fleet.rs#L882),
[fleet.rs:823](../crates/rekcod/src/fleet.rs#L823),
[fleet.rs:847](../crates/rekcod/src/fleet.rs#L847),
[fleet.rs:4147](../crates/rekcod/src/fleet.rs#L4147).

Cancel writes a marker and removes the sandbox if one exists. During clone and
sandbox creation there isn't one yet, so cancel returns success and the worker
carries on. The worker checks the marker only after the command finishes. The
controller marks the job terminal at once, releasing quota and schedule exclusion.

**Reproduced with the current job functions and stubbed clone and VM operations:**
`cancel_response={"cancelled":"j-audit"}`, then `sandbox_created_after_cancel=1`
and `log="executed-after-cancel"`.

Fix: check cancellation after clone, after sandbox creation and before exec, and
keep the controller row `cancelling` until the worker confirms it stopped.

### J2 P2 A missed heartbeat starts a second copy of a scheduled job

Source: [fleet.rs:1747](../crates/rekcod/src/fleet.rs#L1747),
[fleet.rs:4014](../crates/rekcod/src/fleet.rs#L4014),
[fleet.rs:3984](../crates/rekcod/src/fleet.rs#L3984),
[fleet.rs:4140](../crates/rekcod/src/fleet.rs#L4140).

When a node misses heartbeats its jobs become `lost`, a terminal state, though
the worker may still be running them. Schedules skip only `running` jobs, so the
next tick starts another copy elsewhere. Lost jobs are never polled again and
cancel refuses them.

**Reproduced with the actual controller and two mock workers:** fifteen seconds
after worker 1 stopped heartbeating, the schedule started on worker 2. Cancel of
the original returned `400 job ... is lost`. This breaks the non-overlap promise
in [fleet-compute.md](fleet-compute.md).

Fix: treat `lost` as unknown, keep schedule exclusion until the worker confirms
termination or the node is gone, keep polling lost jobs, and let cancel send the
DELETE.

### J3 P2 A lost start acknowledgement leaves an untracked job

Source: [fleet.rs:3971](../crates/rekcod/src/fleet.rs#L3971),
[fleet.rs:789](../crates/rekcod/src/fleet.rs#L789),
[fleet.rs:840](../crates/rekcod/src/fleet.rs#L840).

The controller sends the job to the worker before it stores the row. If the worker
starts it and the reply is lost, the controller drops the ID. A retry allocates a
new ID and runs the job again. Job sandboxes are excluded from orphan cleanup.

**Reproduced with a mock worker that accepted and closed:** two worker jobs ran,
both requests returned 400, and the controller had no job rows.

Fix: insert the row as `pending` with its quota before dispatch, make starts
idempotent by ID, and reconcile `pending` rows against the worker.

### J4 P2 A node restart leaves job sandboxes running

Source: [fleet.rs:837](../crates/rekcod/src/fleet.rs#L837),
[fleet.rs:851](../crates/rekcod/src/fleet.rs#L851),
[fleet.rs:870](../crates/rekcod/src/fleet.rs#L870).

Job sandboxes have `ttl_secs=0` and no fleet marker, and only the thread that
started them removes them. After the node service restarts, polling synthesizes a
terminal result and the sandbox stays.

**Source confirmed.** No VM was used.

Fix: mark job sandboxes, and on node start remove marked job sandboxes with no
live runner, or give them the job's timeout as a TTL.

### DOC1 Namespace deletion doesn't erase secrets from earlier backups

Source: [fleet.rs:1590](../crates/rekcod/src/fleet.rs#L1590),
[fleet.rs:4460](../crates/rekcod/src/fleet.rs#L4460),
[namespaces.md:110](namespaces.md#L110).

The secret key derives from the master key and a namespace salt stored in
`fleet.db`. Backups made with `VACUUM INTO` keep the salt and the ciphertext, so
with the master key an older backup still decrypts a deleted namespace's secrets.
The docs say deletion makes them unrecoverable.

**Source confirmed.** No secret was decrypted.

Fix: correct the claim. True erasure needs per-namespace key material kept outside
the backups.

### Found while reviewing the fixes

Two read-only reviews of the merged diff found these, all fixed with tests:

- The first R2 fix dropped a container's queued output when the client still wrote stdin
  after the container exited.
- S5's strict reads also applied to `rekcod x` in your own projects, so a monorepo's
  `.nvmrc -> ../../.nvmrc` was ignored. Your projects follow links again (regular files
  only); repositories under `~/.rekcod` don't.
- Jobs a controller marked `lost` before the upgrade would have held quota and their
  schedule forever; a migration ends them as `failed`.
- Destroy on a controller started without `--storage` retried forever and kept the name.
- A destroy or retry could finish a newer app of the same name; `finish_destroy` now
  checks the generation.
- A poisoned app lock stopped destroy retries for that app.
- Schedules stored specs that `start_job` would refuse at every run.

### Behaviour changes on upgrade

- The dashboard signs in with `rekcod dashboard` as before, but there's no cookie; a
  second tab picks the token up from `localStorage`.
- `rekcod mcp` and `sandbox serve` need `--allow-macos` for macOS guests, and a fleet
  node's API reaches only fleet sandboxes.
- `app destroy` waits for a deploy of that app already running. App names of exactly 32
  hex digits are refused.
- Snapshot pushes use the generation layout; a rekcod from before this can't pull them.
- Nodes that join after the upgrade get node-named certificates; existing nodes keep
  theirs until they join again.
- A data disk without the host's fresh marker is never formatted; `start --repair` runs
  `e2fsck` against the backup superblocks.
- A custom `REKCOD_HOME` is set to 0700.
